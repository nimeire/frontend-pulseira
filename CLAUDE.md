# Zelo — front-end

Site do **Zelo** (pt-BR): pulseira inteligente (ESP-12E + MPU6050, botão de pânico, 2 LEDs; powerbank no protótipo, bateria no produto) que detecta possíveis quedas e avisa um responsável. **Conceito mudou: a pulseira NÃO tem mais GPS nem localização.** Páginas institucionais (landing, sobre, sensores, FAQ) já refletem isso; as dashboards (`/paciente`, `/responsavel`, `/admin`) também (alertas em vez de localização). `/privacidade` também foi atualizada (sem localização/GPS; 2026-10-25), e só mantém 1 placeholder `[COLCHETES]` (base legal, a confirmar em revisão jurídica); o resto foi preenchido com fatos do back-end atual (HTTP Basic, MongoDB local/Atlas, sem TTL/exclusão automática, sem CPF) — revisar se o back-end mudar. A foto do ESP-12E é provisória (usa a do ESP32). Projeto acadêmico (prova de conceito) da FATEC Praia Grande (DSM).

Stack: React 19 + Vite + TypeScript estrito + react-router-dom. CSS Modules + tokens. Sem UI kit, sem testes.
O back-end fica em outro repositório (`../backend-pulseira`: Java/Spring Boot + MongoDB). **O front agora chama a API de verdade** (`src/services/`). URL base: `VITE_API_URL` (padrão `http://localhost:8080`; ver `.env.example`). Só altere o back-end se o usuário pedir explicitamente.

**API do back-end (HTTP Basic: `Authorization: Basic base64(email:senha)` em toda chamada; `GET /api/auth/me` valida o login e devolve `perfil` RESPONSAVEL|PACIENTE|ADMIN):** `POST /api/auth/cadastro` (público; `nome, cpf, dataNascimento` ISO`, email, telefone, senha, perfil`) · `/api/pessoas-monitoradas/{id}` (GET), `/{id}/informacoes-medicas` (PUT), `/{id}/endereco` (PUT, opcional: tudo em branco remove; CEP só dígitos, UF 2 letras; só a própria pessoa edita, o responsável vinculado vê), `/por-codigo/{codigo}`, `/{id}/responsaveis`, `/{id}/pulseira` · `/api/vinculos` (POST `{codigoVinculo}`, GET `/meus`, DELETE `/{pessoaId}`) · `/api/pulseiras/parear` (POST `{dispositivoId}`), `/{id}/vinculo` (DELETE) · `/api/alertas?pessoaMonitoradaId=` + PUT `/{id}/reconhecer|resolver|falso-positivo` (`cuidadorId` do corpo é ignorado; vale a conta logada) · `/api/admin/usuarios`, `/usuarios/{id}/status`, `/pulseiras` · **conta:** `PUT /api/conta/foto|telefone|email|senha|perfil` (foto = data URL JPEG/PNG/WebP ≤ 300 KB; e-mail e senha exigem `senhaAtual`/mudam o login) · **alertas paginados:** `GET /api/alertas/pagina?pessoaMonitoradaId=&pagina=&tamanho=&ultimas24h=` e `GET /api/alertas/resumo?pessoaMonitoradaId=` (`{pendentes, ultimoAlerta}`). Pacientes e responsáveis trazem `ativo` (conta ativa) e `fotoUrl`. Tipos de alerta: `POSSIVEL_QUEDA`→`queda`, `PANICO`→`botao_panico`; status em maiúsculas → minúsculas. CORS: o back libera só as origens de `ZELO_CORS_ORIGINS` (padrão `http://localhost:5173`). Admin é criado por `ZELO_ADMIN_EMAIL`/`ZELO_ADMIN_SENHA`. O front já faz tudo isso: pergunta o `perfil` no cadastro e converte a data para ISO.
**Como o front fala com a API:** `services/api.ts` (`requisitar`, `ApiError`, `mensagemDeErro`, cabeçalho Basic) e `services/zelo.ts` (uma função por endpoint + conversão dos enums/formatos da API para os tipos do front: `POSSIVEL_QUEDA`→`queda`, `PANICO`→`botao_panico`, `ATIVA`+pessoa→`conectada`, `perfil`→`tipo`, CPF só dígitos→formatado). `AuthContext`/`useAuth` guardam a sessão (`zelo:sessao`: `sessionStorage`, ou `localStorage` com "Lembrar de mim"; é só Base64, não criptografia). `useRecurso` carrega dados + polling (15 s nas dashboards), `useAcao` roda ações e recarrega, `PainelEstado` mostra carregando/erro. `RequireAuth` protege cada dashboard por `perfil`.

## Comandos
- `npm run dev` (porta 5173) · `npm run build` (= `tsc -b && vite build`) · `npm run lint` (oxlint) · `npm run preview`
- **Deploy (GitHub Pages):** `.github/workflows/deploy.yml` (push em `main`, só para o dono do repo) roda `npm ci` + `npm run build`, copia `dist/index.html` → `dist/404.html` (fallback SPA) e publica. `vite.config.ts` usa `base: '/frontend-pulseira/'` **só no build** (`'/'` no dev). Não alterar workflow/`base` sem combinar. `vite preview` usa `base '/'`, então **não serve para testar o Pages**.

## Rotas (`src/router/routes.tsx`)
Dentro de `MainLayout` (header + footer): `/` Landing (só hero) · `/sobre` Sobre o projeto (âncoras `#como-funciona`, `#beneficios`) · `/sensores` · `/contato` · `/privacidade` · `/faq` (`?pagina=N`) · `*` `NotFoundPage` (404 — captura qualquer caminho não mapeado dentro do `MainLayout`; mostra a URL digitada e um botão para voltar à `/`).
Fora do `MainLayout` (standalone, sem header/footer do site): `/login`, `/cadastro` (`AuthLayout`) e as três dashboards com `DashboardLayout` — `/admin`, `/paciente` e `/responsavel`. Também standalone: `/perfil` (qualquer conta logada: `RequireAuth` sem `perfil`), com foto, telefone, e-mail, senha e tipo de conta; o avatar do topo das dashboards leva até ela.
`ScrollToTop` (em `App.tsx`) rola ao topo a cada troca de rota e para `#hash` quando houver. O "Entrar" do Header/CTAs já leva a `/login`.
**Cada dashboard é protegida por `RequireAuth`**: `/admin` só ADMIN, `/paciente` só PACIENTE, `/responsavel` só RESPONSAVEL (outro perfil vai para o próprio painel; sem login vai para `/login`). O login é por **e-mail** + senha (`GET /api/auth/me`; **não há login por CPF**), e depois leva ao painel do perfil. Quem já está logado e abre `/login` ou `/cadastro` é mandado ao próprio painel; o botão "Entrar" do Header vira "Meu painel". O ADMIN não se cadastra pela tela: nasce de `ZELO_ADMIN_EMAIL`/`ZELO_ADMIN_SENHA` no back-end.

## Estrutura de `src/`
- `pages/<nome>/` uma página + `sections/` (só o que é específico dela). Páginas: about, contact, faq, landing, privacy, sensors. `pages/auth/login` e `pages/auth/cadastro` seguem o mesmo padrão (página fina + `sections/LoginFormSection`/`CadastroFormSection` com o formulário em si). `pages/admin`, `pages/paciente` e `pages/responsavel` idem: página fina (`AdminPage`/`PacientePage`/`ResponsavelPage`) + `sections/` com cada bloco (conexões, status/mapa, dados médicos, log). `pages/not-found/NotFoundPage` é a 404 (sem `sections/`, não precisou).
- `components/<kebab-case>/` componentes reutilizáveis (`X.tsx` + `X.module.css`). `layout/` (MainLayout, PageContainer), `auth-layout/` (`AuthLayout` — casca de login/cadastro), `dashboard-layout/` (`DashboardLayout` — casca de `/admin`, `/paciente`, `/responsavel` e `/perfil`: usa o **mesmo `Header` do site** (com o selo `badgeLabel`) + conteúdo em `PageContainer`) + "Sair", conteúdo em `PageContainer`), `header/`, `footer/`, `form-field/` (`FormField`, `PasswordField`), `avatar/` (`Avatar`, aceita `size` opcional p/ usos compactos), `stat-card/` (`StatCard`, aceita `tone?: 'primary' | 'success' | 'alert'` p/ colorir o ícone), `distribution-bar/` (`DistributionBar` — mini gráfico de barra empilhada, CSS puro), `connection-card/` (`ConnectionCard` — card de pareamento genérico: form com código + botão quando desconectado, resumo + "Desconectar" quando conectado; usado só pra pulseira hoje), `patient-code-card/` (`PatientCodeCard` — card do lado do paciente que exibe/compartilha `codigoVinculo` em vez de pedir um código; reaproveita as classes de `ConnectionCard.module.css`), `checklist-field/` (`ChecklistField` — `<fieldset>` de checkboxes, ou radio com `multiple={false}`, pros formulários médicos), `informacoes-medicas-form/` (`InformacoesMedicasForm` — formulário editável do paciente), `informacoes-medicas-view/` (`InformacoesMedicasView` — mesmo dado, somente leitura, pro responsável), `alert-history/` (`AlertHistory` — lista de alertas de queda/pânico; com `onChangeStatus` mostra os botões Reconhecer/Resolvido/Falso positivo), `ui/` (Button, IconButton, LinkButton), `icons/` (todos os SVGs em `index.tsx`).
- `data/` conteúdo e listas tipadas, **fora do JSX** (nomes em pt-BR para conteúdo de domínio: `beneficios.ts`, `passos.ts`, `faq.ts`...; `siteConfig.ts`, `footerData.ts`, `opcoesMedicas.ts` — checklists de tipo sanguíneo/alergias/condições/medicamentos + `rotulosSelecionados()`).
- `hooks/` `useTheme`, `usePageMeta`, `usePaginacao<T>`, `useActiveSection`. `utils/` `classNames`, `paginacao`, `scroll`, `mascaras` (`formatarCpf`, `formatarDataBr`), `tempo` (`tempoRelativo` — "há N minutos"), `idade` (`calcularIdade`). `types/` tipos compartilhados (`politica.ts`, `theme.ts`, `usuario.ts` — conta do `/admin`; `paciente.ts`, `responsavel.ts`, `pulseira.ts`, `alerta.ts` — domínio de `/paciente`/`/responsavel`, espelhando `../backend-pulseira`). `context/` tema.
- `styles/` `tokens.css` (única fonte de cor/espaço/tipografia), `fonts.css`, `reset.css`, `global.css`.
- `assets/fonts` (SF Pro Display, woff2) e `assets/images` (`hardware/`, `team/`, fotos da pulseira — **não usadas** no login/cadastro/dashboards, ver Armadilhas).

## Convenções
- TypeScript estrito, **sem `any`**, sem `@ts-ignore`; props tipadas; componentes pequenos; componentes PascalCase, hooks `useX`.
- Conteúdo em `data/`, nunca hardcoded em JSX longo. Listas com `key` estável (id/texto único).
- **Cores só por tokens** (`var(--color-*)`). Nenhum hex fora de `styles/tokens.css`. Estados (hover/active) derivam da paleta.
- Tipografia só por tokens (`var(--font-size-*)`), que já estão **+30% sobre o valor base** (ex.: `--font-size-md` é `1.3rem`, não `1rem`) — ajuste pedido para o sistema inteiro. Não reintroduzir os valores base nem escalar de novo; `--space-*`/`--radius-*` não foram tocados (só fonte, não espaçamento).
- Tema claro/escuro: atributo `data-theme` no `<html>`, chave `zelo:theme` no localStorage; `index.html` aplica o tema antes do React (evita flash). Tokens do escuro sobrescrevem os mesmos nomes em `[data-theme='dark']`.
- Fonte **San Francisco (SF Pro Display)** local, `font-display: swap`. Não trocar.
- Acessibilidade: HTML semântico, headings em ordem, `alt` descritivo, foco visível, alvos ≥ 44px, `prefers-reduced-motion` respeitado, contraste WCAG AA.
- Imagens abaixo da dobra com `loading="lazy"` e `width/height`; a do topo não.
- Texto das dashboards (`/admin`, `/paciente`, `/responsavel`) é enxuto de propósito: frases curtas, linguagem simples (ex.: "saúde" em vez de "informações médicas", "Histórico" em vez de "Log de monitoramento"), sem repetir no corpo o que o título/ícone já diz. Pedido explícito do usuário pra ficar mais acessível a públicos diferentes — não reverter pra frases mais longas/formais ao editar essas telas.

## Paleta oficial (não inventar cores)
Azul petróleo `#1B4B5A` (primária) · Verde-água `#5FA8A0` (sucesso/cuidado) · **Coral `#FF6B4A` exclusivo de alerta de queda** (`--color-alert*`; nunca decorativo, nem em botão/link/ícone comum). **Só nas telas logadas** (`StatCard`/`AlertHistory` das dashboards): as páginas públicas (sobre, sensores, fluxos, passos) usam a paleta normal mesmo ao falar de alerta — `FlowDiagram`/`StepList` não têm mais tom `alert` · Areia clara `#F7F5F2` (fundo) · Grafite `#2E2E2E` (texto) · Cinza-médio `#6B6B66` (texto secundário, só ≥14px).

**Exceção aprovada pelo usuário:** erro de validação de formulário usa `--color-error` (vermelho próprio, em `tokens.css`; claro `#b3261e`, escuro `#f28b82`) na borda do campo e na barra da mensagem (`FormField`). Só pra erro de formulário — o coral continua exclusivo de queda, e não use `--color-error` fora de formulários.

## Armadilhas
- **Deploy sob subcaminho:** o Pages serve em `/frontend-pulseira/`. Por isso `BrowserRouter` usa `basename={import.meta.env.BASE_URL}` (`main.tsx`) e o logo usa `import.meta.env.BASE_URL` (`siteConfig.logoSrc`). Caminhos absolutos como `'/favicon.svg'` em JS quebram no Pages (sem isso o site abria em branco: `No routes matched`). Em dev `BASE_URL` é `/`. Em novos assets/links de JS, sempre use `BASE_URL`.
- `position: sticky` do Header exige que `html/body/#root` **não** tenham `height: 100%`/`overflow` (já removido do reset; não reintroduzir).
- Breakpoint do menu mobile está duplicado: `matchMedia('(min-width: 768px)')` em `Header.tsx` e `@media (max-width: 767px)` em `Header.module.css`. Mude os dois juntos.
- `zelo:theme` existe em dois lugares: script inline do `index.html` e `ThemeContext.tsx`.
- `footerData.ts` é a fonte única dos desenvolvedores (footer + `/contato`); Backend aparece primeiro (`backendCreators`/`otherCreators`).
- `politicaPrivacidade.ts`: texto entre `[COLCHETES]` vira placeholder destacado. Descreve o modelo de dados do back-end **atual** (só modelagem, sem controllers); revisar se o back-end mudar.
- `FaqListSection` só considera aberto o item da página atual; `usePaginacao` mantém a página em `?pagina=`.
- `ghost` (Button) e `--font-weight-regular` existem mas ainda não têm uso (mantidos de propósito).
- `AuthLayout` (login/cadastro): cartão centralizado (logo, título, descrição, formulário) sobre fundo cinza claro (`--color-surface-muted`; no escuro, `--color-surface`), com sombra suave. Os campos usam a variante **linha** (só a linha de baixo, rótulo pequeno em caixa alta; `FormField`/`ChecklistField` leem `VarianteCampoContext`, que o `AuthLayout` define como `linha`; fora dele, `caixa`). Botão principal em pílula centralizado. Sem ilustração, sem X e sem painel lateral — a pedido, não reintroduzir. Props: `formTitleId`, `formTitle`, `formDescription`, `wide?`, `children`.
- `AdminPage`: a lista vem de `GET /api/admin/usuarios` e `/api/admin/pulseiras` (recarrega a cada 30 s); ativar/desativar e excluir chamam a API (confirmação via `window.confirm` antes de excluir). Sem paginação/busca/filtro (lista pequena, não precisou ainda).
- Badges de status (`AdminUsersSection`, `ConnectionCard`) e o ícone do `SummaryCard` usam `color-success` como texto **sobre** `color-success-soft`, não o inverso — é o padrão já usado no projeto para "soft badge", não confundir com o par `--color-success`/`--color-success-contrast` (esse é p/ texto sobre `--color-success` sólido). O mesmo padrão vale pro alerta de queda (`color-alert` sobre `color-alert-soft`, em `AlertHistory`/`StatCard`) — é o único lugar do projeto que usa a cor coral, de propósito.
- `PacientePage`/`ResponsavelPage`: `Usuario` (`types/usuario`, usado só no `/admin`) e `Paciente`/`Responsavel` (`types/paciente`, `types/responsavel`) são modelos **diferentes** — não confundir. `Usuario` é a linha da tabela de contas do admin; `Paciente`/`Responsavel` espelham `PessoaMonitorada`/`Cuidador` do back-end, com dados médicos/endereço.
- **Vínculo paciente↔responsável**: quem inicia é sempre o responsável. O paciente nunca digita um código pro lado do responsável — ele só vê/compartilha o próprio `codigoVinculo` (`PatientCodeCard`, no card "Responsável" do `/paciente`). O responsável digita esse código no card "Paciente" do `/responsavel` (`ConexaoPacienteSection`), clica em "Buscar paciente"; se o código existir (a API compara sem diferenciar maiúsculas), aparece uma etapa de confirmação com `Avatar` + nome + idade + telefone + bairro/cidade antes de "Confirmar vínculo"; código errado mostra uma mensagem de erro inline (sem usar `--color-alert` — essa cor é só pra queda, ver Paleta). "Cancelar" volta pra etapa de busca.
- `PacientePage`: tudo vem da API (`carregarPainelPaciente`: cadastro, pulseira, responsáveis, **resumo** de alertas). Pareia a pulseira pelo `dispositivoId` (ela precisa já existir no back-end). Aceita **vários responsáveis** (lista em `PatientCodeCard`, cada um com foto e selo "Conta ativa/inativa" e botão Desvincular; o código fica sempre visível para convidar mais). "Status agora" só considera o que aconteceu nos **últimos 30 min** (`JANELA_RECENTE_MS`): alerta mais antigo que isso já aparece como "Tudo bem" ali, mas continua em "Meus alertas". "Meus alertas" usa `AlertasPaginados` (24 h, 5 por página, "Mostrar todos" abre `AlertasModal` com 10 por página). Os dados de saúde que a pessoa digita ficam em estado local (`edicaoSaude`) para o polling não apagar. O endereço (opcional) **não** fica no painel: é editado em `/perfil` (`pages/perfil/sections/EnderecoSection`, só conta PACIENTE) e aparece para o responsável em `DadosPacienteSection`.
- `ResponsavelPage`: acompanha **vários pacientes** (`GET /api/vinculos/meus`), um aberto por vez (`selecionadoId`; `null` = o primeiro). `ConexaoPacienteSection` lista os conectados (foto, selo de conta ativa, "Ver painel"/"Desconectar") e tem o formulário "Conectar outro paciente" (buscar por código → confirmar). Trocar de paciente muda a chave do `useRecurso`, que recarrega o painel. Alertas: `AlertasPaginados` com os botões Reconhecer/Resolvido/Falso positivo (`versaoAlertas` sobe depois de cada ação para a lista recarregar na hora).
- **Avisos (snackbar)**: todo resultado de uma ação ("Salvo!", "Foto atualizada!", erro da API...) vai para o canto superior direito com `useNotificar()` (`notificar.sucesso(msg)` verde-água, `notificar.erro(msg)` vermelho; somem em 4 s/7 s; ficam na camada de cima do navegador, acima de modais). **Não** crie `<p>`/`<Notice>` soltos de sucesso/erro. Só os erros de validação **de campo** ficam embaixo do campo (`FormField error`). `useAcao(recarregar)` devolve `executar(acao, mensagemSucesso?)`, que já avisa sucesso/erro. `PainelEstado` (falha ao carregar a tela, com "Tentar de novo") continua inline.
- **Confirmações**: nunca use `window.confirm/alert/prompt`. Use `useConfirmar()` (`context/ConfirmacaoContext`): `await confirmar({ titulo, mensagem, confirmar?, cancelar? })` devolve `true/false` e abre uma janela no estilo do site (o foco inicial fica em "Cancelar"). Em celular/teclado funciona com Esc e clique fora.
- **Cabeçalho único**: o `Header` é o mesmo no site e nas telas logadas (ordem fixa: logo, "Sobre o projeto", foto/nome ou "Entrar", tema na ponta direita). Não crie outro cabeçalho: os itens mudavam de lugar entre as páginas. `html { scrollbar-gutter: stable }` evita que a barra de rolagem desloque tudo ~15px entre páginas curtas e longas.
- **Ícones**: todos em `components/icons/index.tsx`, no estilo Lucide/Feather (só contorno, traço 1.8, pontas arredondadas, grade 24) — o mesmo do menu do usuário. Ao criar um ícone novo, siga essa família (não misture preenchidos nem outro traço).
- **Nomes e e-mails em listas/tabelas**: ficam em uma linha só, cortados com "…" (`overflow: hidden; text-overflow: ellipsis; white-space: nowrap`) e com `title` mostrando o texto completo. Vale p/ responsáveis (`PatientCodeCard`), pacientes (`ConexaoPacienteSection`) e usuários/pulseiras do `/admin`.
- **Menu de usuário**: logado, o Header do site e as dashboards mostram o `UserMenu` em vez de um botão solto "Meu painel"/"Sair"; "Sair" a partir de uma tela logada leva ao `/login`, a partir do site público só desloga. A página `/perfil` se chama "Editar perfil".
- **Configurações da conta (`/perfil`)**: a foto é recortada em quadrado e reduzida para 256x256 JPEG no navegador (`utils/imagem.ts`) e vai como data URL. Ao trocar **e-mail** ou **senha**, o login muda: o `AuthContext.trocarCredenciais` passa a enviar as credenciais novas (senão a próxima chamada daria 401 e deslogaria). Mudar de tipo (`TipoContaSection`) só é aceito sem pacientes conectados (responsável→paciente) ou sem pulseira nem responsáveis (paciente→responsável); o cadastro de paciente fica guardado e é reativado se voltar.
- **Dashboards sem localização**: a pulseira não tem GPS, então `/paciente` e `/responsavel` mostram alertas (queda/botão de pânico), status, último sinal da pulseira e dados de saúde — sem mapa nem coordenadas. O endereço do paciente (residencial, do cadastro) aparece só nos dados dele p/ emergência. Reconhecer → Resolvido/Falso positivo seguem `StatusAlerta` do back-end.
